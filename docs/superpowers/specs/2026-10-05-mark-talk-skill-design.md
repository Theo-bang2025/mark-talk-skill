# Mark Talk：职场向上沟通 Skill 设计

日期：2026-10-05
状态：用户已通过；首版按本设计实施

## 1. 目标与范围

Mark Talk 是一个开源的聊天辅助 Skill。首版聚焦有职责、指导、评价或决策关系的向上沟通，包括员工与上司、实习生与带教、研究生与导师、辅导员与上级。用户提供少量背景或一段对话后，Skill 帮助其明确当次目标、识别尚缺的信息，并生成少量可直接使用的回复方案。

首版的成功标准是：用户能迅速得到贴合当下关系与目的的建议，知道每个方案的意图与取舍，并能纠正 Skill 对事实或关系的理解。首版不承诺升职、加薪或改变对方行为；这些结果受工作表现、组织环境及对方决定等因素影响。

首版不处理自动读取微信/QQ、自动发送消息、全量聊天记录同步、后台长期跟踪、云端账户和大型书籍知识库。平级沟通、朋友和亲密关系作为后续场景扩展。

## 2. 用户体验

### 2.1 入口

用户可以从一句自然语言开始，例如：“导师让我明天交初稿，但实验数据没齐，怎么回？”也可附上相关聊天片段、用户与对方的关系卡，以及“帮我分析局面”“只给能复制的回复”“更新关系卡”等明确指令。

Skill 不要求用户先填写长表格。它只提取影响本次建议的信息：双方关系、对方原话或关键行为、当前任务、用户实际可承诺的事项、用户本次目标、时效和表达偏好。

### 2.2 追问与快速模式

当缺失信息会显著改变回复时，默认一次提出最多两个最有价值的问题，并说明问题为何重要。若用户表示赶时间，或已经足以给出稳妥建议，则直接回答；对缺失事实以简短假设标明，不自行补造事实。用户可以在任意阶段说“直接给我回复”，Skill 随即进入快速模式。

### 2.3 输出

默认提供两到三条中文回复，措辞自然、长度适合当前媒介、可直接复制。每条附一句适用条件或主要取舍。选项的区分取决于场景，例如稳妥说明、主动协商、明确边界；不强制生成固定三种话术。必要时先用两三句说明关键局面与风险，避免长篇心理揣测。

用户选中方案后，可以要求缩短、变得更坚定/委婉、贴近自己的口吻，或模拟对方可能的后续回应。Skill 对“对方可能怎么想”只给有依据的可能性，不当作事实。

## 3. 沟通判断框架

Skill 在内部依次判断：

1. 区分已知事实、用户转述、推测与未知事项。
2. 识别双方角色、权责、关系历史以及本次沟通的具体目标。
3. 找到影响措辞的约束：时限、可兑现的承诺、组织规范、敏感信息及关系风险。
4. 决定是追问还是先给条件化建议。
5. 生成少量不同策略的回复，检查其事实准确性、可执行性、语气和潜在误解。

允许用户选择谈判、试探或坚定表达，但不建议虚构成果、编造承诺、冒充他人或凭一次对话断定对方人格。需要用户承担的承诺必须与其已提供的事实一致。

## 4. 关系卡与数据边界

首版使用可复制的文本“关系卡”，字段包含：对象代称及角色、用户在这段关系中的角色、长期目标、表达偏好、已确认的互动事实、待验证的判断、当前未解决事项和最近更新时间。每条待验证判断都应能回到用户提供的依据，避免把猜测写成稳定画像。

Skill 可以根据新材料提出关系卡修订建议，先展示变更，再由用户决定是否采用。用户可直接要求查看、纠正或删除卡片内容。首版关系卡由用户自行保存和带入后续对话；Skill 不宣称已跨会话永久保存，也不能替宿主平台删除聊天历史。用户应能在不提供关系卡的情况下继续使用通用回复功能。

默认只请求与当前问题相关的片段，提示用户移除无关姓名、联系方式、公司秘密、学术未公开数据和其他敏感内容。公开仓库及测试材料仅放虚构或充分匿名化案例，不收集朋友内测的原始聊天记录。若后续建立应用，优先评估用户设备本地保存、明确的导入/导出/删除操作及最短必要保存期，再决定是否需要云同步；云端方案需单独完成数据流、平台条款与适用法律审查。

## 5. 载体和阶段

### 第一阶段：可移植的 Skill 核心

以符合 Agent Skills 规范的 `SKILL.md` 承载触发条件、交互流程、判断规则和输出约定。按实际需要添加简短参考文件与虚构样例，不依赖脚本、数据库、API 密钥或账户。仓库提供安装说明、使用示例、隐私提示和测试方法。优先在支持导入技能的环境实测，不把开发平台能力等同于消费者 App 能力。

### 第二阶段：可控关系档案

基于首版试用结果，建立用户可查看、编辑、删除和导出的持久档案。优先研究本地保存，避免默认收集完整原始聊天记录。关系档案作为独立数据层，不把用户私有信息打包进公共 Skill。

### 第三阶段：平台适配与长期记忆

针对每个平台验证真实安装路径、手机端操作、文件输入、记忆行为与数据删除能力。需要时制作平台专属智能体或适配器，但保留同一套核心沟通规则。长期记忆通过用户可审阅的摘要逐步更新，不依赖不可控的自动画像。资料库只在评测显示具体知识缺口时加入。

## 6. 错误与特殊情况

- 信息不足：询问最多两个关键问题，或在快速模式给出标明假设的保守方案。
- 聊天片段过长：先请用户指出最近需要回复的消息与本次目标，或提炼必要事实；不把长记录中的每句都写入关系卡。
- 来源冲突：指出冲突并请求澄清，不将推断覆盖用户确认的事实。
- 高风险或敏感内容：提醒用户核对可公开范围，优先使用去标识化摘要；不要求上传完整原文才能提供帮助。
- 平台没有持久化能力：输出可复制关系卡，清楚说明保存需由用户完成。

## 7. 验证与发布标准

先构造覆盖延期交付、争取资源、澄清误解、汇报成绩、拒绝不合理要求、与导师讨论进度等情境的虚构案例，包含信息充足与信息不足两类。逐例检查：是否问到关键问题、是否区分事实与推测、是否遵守两到三个选项、回复是否可复制且符合关系、是否出现无法兑现的承诺、关系卡修订是否可审阅。

邀请少量朋友试用时，仅收集经其自愿提供的评分或匿名反馈：哪条被选、是否需要改写、问题是否有帮助、是否感觉符合本人语气；不要求提交原始聊天记录。与未启用 Skill 的普通模型回复做相同案例比较，并记录失败例以迭代。发布前验证 Skill 格式、至少一个真实宿主中的触发与对话效果，以及 GitHub 安装文档的实际步骤。平台兼容性只声明已实测的组合。

## 8. 项目默认选择与后续决策点

项目暂用中文名“Mark Talk 职场沟通助手”、仓库名 `mark-talk-skill`，以 MIT 许可证作为开源发布提案；实际公开发布前再核对仓库内容和许可证。首批验证宿主为当前可用的 Codex 环境，以及官方明确支持从 GitHub 安装 Skill 的千问办公。其他平台只有在实测通过后才列为兼容。

第二阶段档案的本地文件格式、设备交互方式和是否提供同步，应由首版内测中实际出现的使用障碍决定。在这些选择确定前，不将任何平台内建记忆描述为项目自己的可控档案。
